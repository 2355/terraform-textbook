# 2. Terraform のための AWS 超入門

> **この章でわかること**
> アカウント、リージョン、IAM、VPC といった AWS の基本概念と、Web アプリで使う代表的なサービス、料金で失敗しないための考え方。Terraform から見ると AWS は「巨大な API」であること。

Terraform は AWS 以外のクラウドも扱えますが、この本では AWS を題材にします。

Terraform のコードは、AWS のサービスの設定をそのまま書き下したものです。つまり **AWS を知らないと Terraform のコードは読めません**。この章では、後の章を読むのに必要な最低限だけを駆け足で押さえます。

---

## 2.1 クラウドとは、巨大な API である

クラウドとは、**サーバやネットワークやデータベースを、必要なときに必要なだけ借りられるサービス**です。

Web エンジニアの感覚で言えば、Vercel や Heroku のもっと低レイヤ版です。Vercel は「Next.js のアプリを置けば動く」まで面倒を見てくれます。AWS は「仮想サーバ 1 台」「ネットワーク 1 つ」「ファイアウォールのルール 1 行」といった**部品単位**で貸し出します。自由度が高いぶん、組み立ては自分でやる必要があります。

### コンソールも CLI も、裏では同じ API を叩いている

ここが Terraform を理解するうえで最も重要なポイントです。

AWS のあらゆる操作は、**HTTP の API 呼び出し**です。コンソールでボタンを押すのも、`aws` CLI でコマンドを打つのも、裏では同じ API を呼んでいます。

```
コンソール（ブラウザ）  ─┐
aws CLI                ─┼─→  AWS の API（例: CreateBucket）
Terraform              ─┘
```

Terraform も特別なことはしていません。HCL に書かれた「あるべき姿」と現実を比べて、**必要な API を必要な順に呼んでいるだけ**です。React が最終的に `document.createElement` を呼んでいるのと同じで、魔法はありません。

この理解があると、Terraform のエラーも読めるようになります。「AccessDenied」なら API を呼ぶ権限がない。「BucketAlreadyExists」なら API が名前の重複を拒否した。**エラーの多くは AWS の API がそのまま返したもの**です。

## 2.2 アカウント、ルートユーザ、リージョン

### AWS アカウント

**AWS アカウント**は、リソースと請求をまとめる単位です。GitHub の Organization に近く、作ったものはすべてどこかのアカウントに属し、料金もアカウントごとに請求されます。アカウントは 12 桁の数字の ID で識別されます。

本格的な運用では、本番用と開発用でアカウントを分けるのが一般的です（第 11 章で扱います）。

### ルートユーザは普段使わない

アカウントを作るときに登録したメールアドレスとパスワードでログインする ID を、**ルートユーザ**と呼びます。ルートユーザはアカウント内で**何でもできる**特権 ID です。

AWS の公式ドキュメントは、**ルートユーザを日常の作業に使わないよう強く推奨**しています。ルートユーザには MFA（多要素認証）を設定して金庫にしまい、普段の作業は後述の IAM Identity Center で作った管理用ユーザで行います。

Linux の `root` で常にログインしないのと同じ理屈です。

### リージョンとアベイラビリティゾーン

AWS のデータセンターは世界中に分散しています。

- **リージョン** — 地理的な地域。東京は `ap-northeast-1`、大阪は `ap-northeast-3`、米国バージニア北部は `us-east-1`
- **アベイラビリティゾーン（AZ）** — リージョン内にある、互いに独立したデータセンター群。`ap-northeast-1a` のように末尾にアルファベットが付く（この名前と実際の AZ の対応はアカウントごとに異なり、アカウントをまたいで同じ AZ を指すには `apne1-az1` のような AZ ID を使う）

```
リージョン ap-northeast-1（東京）
├── AZ ap-northeast-1a  ── データセンター群
├── AZ ap-northeast-1c  ── データセンター群
└── AZ ap-northeast-1d  ── データセンター群
```

AZ は電源やネットワークが独立しているので、1 つが障害で落ちても他は動き続けます。**本番のサーバや DB を複数の AZ に分散させる（マルチ AZ）**のは、このためです。

ほとんどのリソースは**どこかのリージョンに属します**。東京リージョンで作った EC2 は、コンソールで大阪リージョンを選んでいると見えません。「作ったはずのものがない」ときは、まずリージョンを疑ってください。

一方で IAM のように**リージョンに属さないグローバルなサービス**もあります。CloudFront で使う TLS 証明書は `us-east-1` で作る必要がある、といった癖もあり、Terraform で複数リージョンを扱う場面が出てくるのはこのためです。

## 2.3 IAM — 誰が、何を、してよいか

**IAM（Identity and Access Management）**は、AWS の認証と認可の仕組みです。AWS へのすべての API 呼び出しは、IAM によって「この呼び出しは許可されているか」を判定されます。

### 登場人物

- **IAM ユーザ** — 人やプログラムに対応する、長期的な認証情報（パスワードやアクセスキー）を持つ ID
- **IAM ロール** — 「かぶる帽子」のようなもの。引き受けた（assume した）人やサービスに、**一時的な認証情報**が発行される
- **ポリシー** — 「どの操作を、どのリソースに対して許可するか」を書いた JSON の文書

ポリシーはこんな形をしています。

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::my-app-assets/*"
  }]
}
```

「`my-app-assets` バケットのオブジェクトを読むこと（`s3:GetObject`）を許可する」という意味です。`Version` は日付に見えますが、ポリシー言語のバージョンを表す固定値です。

### 長期の鍵より、一時的な認証情報

AWS の IAM ベストプラクティスは、**人間は ID プロバイダ経由で一時的な認証情報を使い、ワークロード（アプリや CI）は IAM ロールで一時的な認証情報を使う**ことを求めています。人間のアクセス管理には **IAM Identity Center** が推奨されています。

アクセスキー（長期の鍵）を発行して `.env` に書くのは、**期限切れしない API トークンを Git に置くのと同じ危うさ**があります。漏れたら、気づいて無効化するまで使われ放題です。具体的な認証の設定は第 4 章、CI からの認証は第 13 章で扱います。

### 最小権限

IAM の基本原則は**最小権限（least privilege）**です。必要な操作だけを、必要なリソースにだけ許可します。

最初から完璧にする必要はありません。AWS 自身も「広めの権限から始めて、徐々に絞る」アプローチを示しています。ただし `"Action": "*"` を本番のアプリに付けたまま放置するのは避けてください。

## 2.4 ネットワークの基礎: VPC、サブネット、セキュリティグループ

Web エンジニアが一番とっつきにくいのがここです。

### VPC

**VPC（Virtual Private Cloud）**は、AWS の中に作る**自分専用の閉じたネットワーク**です。家庭の LAN を AWS 上に作るイメージです。

VPC には `10.0.0.0/16` のような **CIDR** でアドレスの範囲を割り当てます。`/16` は「先頭 16 ビットが固定」という意味で、`10.0.0.0` から `10.0.255.255` までの約 6 万 5 千個のアドレスを使えます。

### サブネット

VPC をさらに区切ったものが**サブネット**です。サブネットは必ず 1 つの AZ に属します。

- **パブリックサブネット** — インターネットとの出入り口（インターネットゲートウェイ）への経路があるサブネット。ロードバランサなどを置く
- **プライベートサブネット** — インターネットから直接到達できないサブネット。アプリのサーバや DB を置く

```
VPC 10.0.0.0/16
├── パブリックサブネット（AZ-a）10.0.1.0/24 … ALB
├── パブリックサブネット（AZ-c）10.0.2.0/24 … ALB
├── プライベートサブネット（AZ-a）10.0.11.0/24 … アプリ、DB
└── プライベートサブネット（AZ-c）10.0.12.0/24 … アプリ、DB
```

パブリックかプライベートかは、サブネットの属性ではなく**ルートテーブル（通信の経路表）の設定で決まります**。ここは初見で混乱しやすい点です。

### セキュリティグループ

**セキュリティグループ**は、リソースごとに付けるファイアウォールです。「どこから、どのポートへの通信を許可するか」を許可ルールとして書きます。

- ALB: インターネットから 443 番ポート（HTTPS）を許可
- アプリ: **ALB のセキュリティグループから**の 3000 番ポートだけを許可
- DB: **アプリのセキュリティグループから**の 5432 番ポートだけを許可

IP アドレスではなく「どのセキュリティグループからか」で許可を書けるのがポイントです。こうして**通信の経路を必要最小限に絞る**のが、AWS のネットワーク設計の基本です。

## 2.5 Web アプリを動かすのに必要なサービス

AWS には数百のサービスがありますが、典型的な Web アプリで使うものは限られます。リクエストの流れに沿って見ていきます。

```
ユーザ
  │
  ▼
Route 53（DNS）
  │
  ├──→ CloudFront（CDN）──→ S3（静的ファイル: React のビルド成果物）
  │
  └──→ ALB（ロードバランサ）
          │
          ▼
       ECS on Fargate（コンテナ: Node.js の API）
          │
          ▼
       RDS（PostgreSQL / MySQL）
```

Route 53 は通信を中継するわけではなく、ドメイン名から宛先（CloudFront や ALB）を引けるようにする役です。図は「どこへ向かうか」の流れとして見てください。API を ECS の代わりに Lambda で動かす構成もよく使われます。

| サービス | 何をするか | Web エンジニア向けのたとえ |
|---|---|---|
| **Route 53** | DNS。ドメインと宛先を対応付ける | お名前.com の DNS 設定画面 |
| **CloudFront** | CDN。世界中のエッジでキャッシュして配信 | Cloudflare の CDN |
| **S3** | オブジェクトストレージ。ファイルを置く | 容量無制限の巨大なファイル置き場 |
| **ALB** | HTTP のロードバランサ | nginx のリバースプロキシ |
| **EC2** | 仮想サーバ。OS から自分で管理する | VPS |
| **ECS / Fargate** | コンテナを動かす。Fargate ならサーバ管理不要 | `docker run` を AWS がやってくれる |
| **Lambda** | 関数単位で実行。リクエストがあるときだけ動く | Vercel Functions |
| **RDS** | マネージドなリレーショナル DB | バックアップやパッチを任せられる PostgreSQL |

最近の Web アプリでは、**EC2 で OS を直接管理するより、ECS on Fargate や Lambda に任せる**構成が増えています。管理するものが減るほど、Terraform で書くものも減ります。このような構成を Terraform で組む全体像は第 10 章で扱います。

## 2.6 料金の考え方

### 従量課金

AWS の料金は基本的に**使った分だけ**です。サーバなら起動していた時間、S3 なら保存した容量とリクエスト数、通信ならデータ転送量で課金されます。

便利な反面、**「動かしっぱなし」がそのまま請求になる**ということでもあります。

### 消し忘れが最大の敵

学習中に一番多い事故は、試しに作ったリソースの消し忘れです。特に注意したいのは、**使っていなくても時間単位で課金されるもの**です。RDS のインスタンス、ALB、プライベートサブネットからインターネットに出るための NAT ゲートウェイなどが代表例です。

ここで Terraform が役に立ちます。Terraform で作ったものは `terraform destroy` で**まとめて消せます**。コンソールで作ったものを 1 つずつ探して消すより、ずっと確実です（中身が残った S3 バケットなど、そのままでは消せない例外もあります）。

### 無料枠と Budgets

新規アカウントには**無料枠**があります。2025 年 7 月 15 日以降に作成したアカウントでは、サインアップ時に「無料プラン」か「有料プラン」を選び、どちらでも一定額のクレジットが付与される形になりました。無料プランは最長 6 か月で、期間が過ぎるかクレジットを使い切ると終了し、有料プランへアップグレードしない限りアカウントは閉じられます。細かい条件は変わることがあるので、公式ページで確認してください。

そして、アカウントを作ったら最初に **AWS Budgets** で予算アラートを設定してください。月の予算額を決めておくと、**実際の請求額や予測額**がしきい値を超えたときにメールで通知されます。

ただし Budgets の通知は**請求データが反映されてから届く**ため、即時ではありません。アラートは保険であって、上限を保証するものではないと理解しておきましょう。

## 2.7 ARN とタグ

最後に、Terraform のコードに頻繁に登場する 2 つの概念です。

### ARN

**ARN（Amazon Resource Name）**は、AWS のリソースを一意に識別する名前です。

```
arn:aws:s3:::my-app-assets
arn:aws:iam::123456789012:role/app-task-role
arn:partition:service:region:account-id:resource
```

リソースの「完全修飾名」だと思ってください。S3 バケットはリージョンもアカウント ID も空、IAM はリージョンが空、というように一部が省略されるリソースもあります。

IAM ポリシーで「このリソースに対して許可する」と書くときや、リソース同士を関連付けるときに ARN を使います。Terraform では ARN を手で書くことはあまりなく、**作ったリソースの属性として参照する**のが普通です（第 6 章で扱います）。

### タグ

**タグ**は、リソースに付けるキーと値のラベルです。

```hcl
tags = {
  Project     = "my-app"
  Environment = "prd"
  ManagedBy   = "terraform"
}
```

タグは地味ですが重要です。

- **コストの内訳**をタグ単位で集計できる（設定すれば「プロジェクト別の請求額」が見える）
- **誰が何のために作ったか**がわかる
- `ManagedBy = "terraform"` のように付けておけば、**コンソールで触ってはいけないもの**だと一目でわかる

タグ付けの習慣は、後から付けるより最初から付けるほうがはるかに楽です。

## まとめ

- AWS のあらゆる操作は **API 呼び出し**。Terraform もコンソールも CLI も、同じ API を叩いている
- **ルートユーザは普段使わない**。人は IAM Identity Center、アプリや CI は IAM ロールで**一時的な認証情報**を使う
- リソースの多くは**リージョン**に属し、可用性のために複数の **AZ** に分散させる
- **VPC** は自分専用のネットワーク。パブリック / プライベートの**サブネット**と**セキュリティグループ**で通信を絞る
- 典型的な Web アプリは Route 53 → CloudFront / ALB → ECS / Lambda → RDS / S3 の組み合わせ
- 従量課金なので**消し忘れが最大の敵**。最初に Budgets でアラートを設定する
- **ARN** はリソースの完全修飾名、**タグ**はコスト集計と管理のためのラベル
