# 1. インフラをコードにするということ

> **この章でわかること**
> インフラを手作業で管理すると何が破綻するのか。IaC（Infrastructure as Code）と「宣言的」の意味、そして IaC で得られるものと払う代償。

Terraform の文法に入る前に、Terraform が**何の問題を解くための道具なのか**を押さえます。

ここを飛ばすと、後の章で出てくる state や plan が「なぜこんな面倒な仕組みがあるのか」わからなくなります。逆に、ここが腹落ちすれば、Terraform の設計のほとんどは自然に見えてきます。

---

## 1.1 インフラとは何か

Web エンジニアにとって、アプリは「書いたコード」です。インフラは「**そのコードが動くために必要な、コード以外のすべて**」だと考えてください。

Node.js の API サーバを 1 つ公開するだけでも、裏ではこれだけのものが要ります。

- **サーバ**（またはコンテナの実行環境）— `node server.js` を動かす場所
- **ネットワーク** — サーバ同士やインターネットとをつなぐ配線と、通してよい通信のルール
- **データベース** — PostgreSQL や MySQL の本体
- **ロードバランサ** — 複数のサーバにリクエストを振り分ける
- **DNS** — `api.example.com` をサーバの IP アドレスに変換する
- **TLS 証明書** — `https://` にするための証明書
- **ストレージ** — 画像やファイルの置き場所
- **権限** — 「このサーバはこの DB に接続してよい」といった許可

ローカル開発では `docker compose up` で済んでいたものが、本番では一つひとつ「作って、設定して、つなぐ」対象になります。

そして重要なのは、これらが**一度作って終わりではない**ことです。サーバを増やす、DB を大きくする、ドメインを追加する、権限を絞る。インフラはアプリと同じように、ずっと変更され続けます。

### なぜ Web エンジニアがインフラを知る必要があるのか

昔は「インフラはインフラ担当の仕事」と分業されていました。今は小さなチームほど、アプリを書いた人がそのまま本番環境まで面倒を見ることが増えています。

「環境変数を 1 つ足したい」「新しいサブドメインが欲しい」「バッチ用のキューを作りたい」。アプリの機能追加は、かなりの頻度でインフラの変更を伴います。そのたびに担当者に依頼して待つより、**アプリと同じ PR でインフラも変更できる**ほうが速く、間違いも減ります。それを可能にするのが、この本で扱う IaC です。

## 1.2 手作業の時代

### 物理サーバの時代

かつてインフラとは、データセンターに置かれた物理的な機械でした。サーバを買い、ラックに載せ、ケーブルを挿し、OS をインストールする。新しいサーバが使えるまでに数週間かかるのも普通でした。

この時代、変更は遅く、サーバは高価で数も少ない。だから**1 台ずつ丁寧に手で設定する**ことが、それほど不合理ではありませんでした。

### クラウドのコンソールの時代

クラウドの登場で状況が一変します。ブラウザで管理画面（コンソール）を開き、ボタンを押せば、数分でサーバや DB が手に入るようになりました。

これは劇的な進歩です。ただし、**作り方は相変わらず手作業**でした。

- コンソールでポチポチとサーバを作る
- 設定項目を目で確認しながら入力する
- 手順は Wiki や Excel に「作業手順書」として残す

作るのが簡単になったぶん、インフラの数は爆発的に増えました。手作業のまま数だけ増えた結果、次の節で見る問題が一気に表面化します。

---

## 1.3 手作業の何が問題か

### 再現できない

「本番と同じ構成で検証環境を作って」と言われたとします。手順書はあるものの、半年前の記述で、途中で誰かが画面に従って変えた設定は書かれていない。結局、本番のコンソールを開いて、設定を 1 つずつ目で見比べることになります。

Web 開発に置き換えると、**`package.json` がなく、「どのライブラリを入れたか」を README に手書きしている**状態です。`npm install` 一発で同じ環境が再現できる世界から見ると、かなり危うい状況です。

### レビューできない

アプリのコードは PR でレビューしてからマージします。ところがコンソールでの操作は、**押した瞬間に本番に反映されます**。

誰かがセキュリティグループ（通信の許可ルール）を誤って全開放しても、事前に止める仕組みがありません。事後に気づけるかどうかも運次第です。

### 属人化する

「あの DB の設定はなぜこうなっているのか」を知っているのは、作った本人だけ。その人が異動すると、誰も触れない「開かずの間」ができます。

### drift する

**drift**（ドリフト）とは、「あるべき姿」と「実際の姿」が少しずつずれていくことです。

障害対応の深夜に、とりあえずコンソールで設定を変えた。手順書の更新は後回しにして、そのまま忘れた。これが積み重なると、手順書も誰の記憶も、現実と一致しなくなります。

### スノーフレークサーバ

こうして生まれるのが**スノーフレーク（雪の結晶）サーバ**です。雪の結晶が一つひとつ違う形をしているように、**同じ役割のはずなのに 1 台ずつ微妙に設定が違う**サーバのことです。

スノーフレークサーバは、壊れたら同じものを二度と作れません。だから誰も触りたがらず、OS の更新も止まり、ますます特殊な存在になっていきます。

## 1.4 IaC という考え方

これらの問題への答えが **IaC（Infrastructure as Code）** です。名前のとおり、**インフラの構成をコードとして書き、そのコードからインフラを作る**という考え方です。

コードになった瞬間、ソフトウェア開発で当たり前に使っている道具がすべてインフラにも使えるようになります。

| 手作業の問題 | コードにすると |
|---|---|
| 再現できない | 同じコードを実行すれば同じ構成ができる |
| レビューできない | PR で差分を見てからマージできる |
| 属人化する | コードとコミット履歴が「なぜこうなったか」を語る |
| drift する | コードと現実を比べて、ずれを検出できる |
| スノーフレーク | 壊れても同じコードで作り直せる |

**インフラの変更が `git log` に残り、`git revert` の対象になる**。これが IaC のいちばん大きな価値です。

### ペットと家畜

IaC の文脈でよく使われる比喩に「**ペットと家畜（pets vs cattle）**」があります。

ペットのサーバには名前があり、病気になれば手厚く看病します。家畜のサーバには番号しかなく、調子が悪ければ入れ替えます。冷たく聞こえますが、**いつでも同じものを作り直せる**からこそ取れる態度です。IaC はサーバを家畜として扱うための前提条件です。

## 1.5 命令的か、宣言的か

インフラをコードにする方法は 1 つではありません。大きく 2 つのスタイルがあります。

### 命令的: 手順を書く

シェルスクリプトから AWS の CLI を呼ぶのが典型です。

```sh
# 手順を順番に書く。2 回目に実行したときどうなるかは、書き手が考えて手当てする必要がある
aws s3api create-bucket --bucket my-app-assets --region ap-northeast-1 \
  --create-bucket-configuration LocationConstraint=ap-northeast-1
aws s3api put-bucket-versioning --bucket my-app-assets \
  --versioning-configuration Status=Enabled
```

これは「何をするか」の列挙です。わかりやすい反面、すぐに限界が来ます。

- 2 回目の実行を想定していない。「もう存在するなら作らない」分岐を自分で書く必要がある
- 「バージョニングを無効に戻したい」とき、元に戻す手順を別に書く必要がある
- 途中で失敗したら、どこまで進んだかを人間が調べる必要がある

つまり**現在の状態を把握して、そこから目標までの手順を考える責任が、すべて書き手にある**のです。

### 宣言的: あるべき姿を書く

Terraform はこちらです。

```hcl
# 「こういうバケットが存在してほしい」という姿だけを書く
resource "aws_s3_bucket" "assets" {
  bucket = "my-app-assets"
}
```

手順は書きません。**最終的にどうなっていてほしいか**だけを書きます。今の状態と見比べて、何を作り、何を変え、何を消すかを決めるのはツールの仕事です。

### 冪等性

宣言的なツールは、何度実行しても、すでに望む姿になっていれば何もしません。この「**何回実行しても結果が同じになる**」性質を**冪等性（べきとうせい、idempotency）**と呼びます。

HTTP メソッドで考えるとわかりやすいです。`PUT /users/1` は何度送っても「ユーザ 1 がこの内容になっている」状態に収束します。`POST /users` は送るたびにユーザが増えます。命令的なスクリプトは `POST` 的で、宣言的なツールは `PUT` 的です。

冪等であることは、運用上とても効きます。途中で失敗しても、**原因を直してもう一度実行すればよい**からです。「どこまで進んだか」を人間が調べる必要がありません。

### React を書いている人には馴染みのある話

これは React が UI でやったことと同じ発想です。

jQuery の時代は「ボタンが押されたら、この要素を消して、あの要素にクラスを足す」と DOM 操作の手順を書いていました。React では「この状態のとき UI はこう見える」と書くだけで、DOM をどう書き換えるかは React が決めます。

```
UI     = f(state)   … 差分を計算して DOM を更新するのは React
インフラ = f(コード)  … 差分を計算して API を呼ぶのは Terraform
```

この「**あるべき姿と現在の姿を比べて、差分を埋める**」処理を **reconciliation（突き合わせ）** と呼びます。React の reconciliation と同じ発想なので、IaC の説明でも同じ言葉が使われることがあります。

### 似ているが違う点

ただし、決定的な違いが 1 つあります。

React の差分適用は、ブラウザの中で一瞬で終わり、失敗してもリロードすれば元に戻ります。インフラの差分適用は、**実際にクラウドの API を呼び、お金がかかり、数分〜数十分かかり、消したデータは戻りません**。

だから Terraform は、差分を適用する前に「**これから何をするか**」を必ず人間に見せる仕組み（plan）を中心に据えています。`git diff` を見てからコミットするのと同じ感覚です。詳しくは第 3 章と第 4 章で扱います。

## 1.6 IaC で得られるもの、払う代償

### 得られるもの

- **再現性** — dev / stg / prd を同じコードから作れる
- **レビュー** — インフラの変更が PR の差分として見える
- **履歴** — いつ、誰が、なぜ変えたかがコミットに残る
- **自動化** — CI から変更を適用でき、人間がコンソールに入る機会を減らせる
- **ドキュメント** — コードそのものが「今の構成」の正確な説明書になる

### 払う代償

いいことばかりではありません。

- **学習コストがかかる**。ツール自体に加えて、クラウドのサービスそのものの理解も必要です。コンソールなら画面が教えてくれた設定項目を、自分で調べて書くことになります
- **ちょっとした変更が遅くなる**。コンソールなら 10 秒の変更が、コードを書いて PR を出してレビューを待つ 30 分の作業になります
- **コードと現実の二重管理になる**。誰かがコンソールで手作業をすると、コードと現実がずれます。IaC を導入したら「コンソールで変更しない」というチームの規律が必要です
- **事故の規模が大きくなる**。手作業なら 1 台ずつ壊れますが、コードは全部まとめて壊せます。1 行の変更が DB の作り直しにつながることもあります

最後の点は特に大事です。**IaC は「速く、正確に、大量に」変更できる道具です。間違った変更も、速く、正確に、大量に適用されます**。だからこそ plan を読む習慣とレビューの仕組みが欠かせません。

### 手作業のほうがよい場面もある

すべてを最初からコードにする必要はありません。

- 新しいサービスを**試しに触ってみる**ときは、コンソールのほうが速く、設定項目の意味も画面から学べます
- 一度しか作らず、二度と変更しないもの（例: アカウント作成直後の初期設定の一部）は、コード化のコストに見合わないことがあります

おすすめは「**コンソールで試して理解し、使うと決めたらコードにする**」という順番です。既存の手作業リソースを後から Terraform に取り込む方法は第 12 章で扱います。

それでも、ある程度の規模を超えたインフラを手作業で管理し続けるほうが、長期的にははるかに高くつきます。これが IaC が業界標準になった理由です。

---

## まとめ

- インフラとは「**アプリのコードが動くために必要な、コード以外のすべて**」で、作った後も変更され続ける
- 手作業の管理は、**再現できない、レビューできない、属人化する、drift する**という問題を抱える
- IaC はインフラをコードにして、Git や PR といった**ソフトウェア開発の道具をインフラに持ち込む**
- 命令的なスクリプトは「手順」を書き、Terraform のような宣言的ツールは「**あるべき姿**」を書く
- `UI = f(state)` と同じく、**インフラ = f(コード)**。差分を計算して適用するのはツールの仕事
- ただしインフラの変更は取り消せない。だから **plan で事前に差分を見る**ことが Terraform の中心にある

次章では、Terraform で操作する相手である AWS の基本を、クラウド未経験者向けに駆け足で押さえます。
