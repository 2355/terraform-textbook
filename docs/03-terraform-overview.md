# 3. Terraform の全体像

> **この章でわかること**
> Terraform がどんな部品でできていて、どんな流れで使うのか。何が得意で、何を任せるべきでないのか。

第 1 章で「宣言的にインフラを書く」という考え方を、第 2 章で AWS の基本を押さえました。この章では、その 2 つをつなぐ道具である Terraform を、細部に入る前に**上空から眺めます**。

コマンドの打ち方は次章で扱います。ここでは「なぜこういう構造なのか」を掴んでください。

---

## 3.1 Terraform とは何か

ひとことで言うと、**「あるべきインフラの姿」を書いたファイルを読み、現実をその姿に近づけるツール**です。

HashiCorp 社が 2014 年に公開しました。最初のバージョンが対応していたのは AWS や DigitalOcean など数種類のサービスだけでしたが、当初から「複数のサービスをまたいでインフラ全体を記述する」ことを掲げていました。

設定は **HCL**（HashiCorp Configuration Language）という専用の言語で書きます。

```hcl
# 「この名前の S3 バケットが存在すべき」と宣言している
resource "aws_s3_bucket" "assets" {
  bucket = "my-app-assets"
}
```

ここには「バケットを作れ」という命令はありません。**「このバケットがある状態」を書いているだけ**です。すでに存在すれば何もしませんし、なければ作ります。第 1 章の `UI = f(state)` と同じ発想で、Terraform は「インフラ = f(コード)」を実現する reconciler（差分を埋める仕組み）だと言えます。

### 本体は 1 つのバイナリ

Terraform 本体は Go で書かれた**単一の実行ファイル**です。Node.js のようなランタイムは要りません。`terraform` コマンドを PATH に置けば動きます。

---

## 3.2 ライセンス変更と OpenTofu

Terraform を調べると必ず出てくる話なので、ここで簡潔に整理しておきます。

- **2023 年 8 月**、HashiCorp は製品のライセンスを MPL 2.0（オープンソース）から **BSL 1.1（Business Source License）** に変更すると発表しました。Terraform では 1.6 以降が BSL です
- BSL は「自社内で使うのは自由。ただし HashiCorp と競合する商用サービスとして提供するのは不可」という趣旨のライセンスです。**普通に自社のインフラを管理する用途なら、これまでどおり無償で使えます**
- これに反発したコミュニティが、MPL 時代のコードからフォークして **OpenTofu** を立ち上げました。Linux Foundation 傘下で開発され、2025 年には CNCF の Sandbox プロジェクトにもなっています
- **2025 年 2 月**、IBM による HashiCorp の買収が完了しました

Elasticsearch から OpenSearch が、Redis から Valkey が生まれたのと同じ構図です。OpenTofu は `tofu` コマンドで、HCL の書き方もほぼ共通です。ただし分岐から時間が経ち、**それぞれにしかない機能**も増えています。

この本では Terraform を前提に進めます。両者の比較と選び方は第 15 章で扱います。

## 3.3 構成要素: Core、provider、Registry

Terraform は大きく 3 つの部品でできています。

```
   あなたの .tf ファイル
          │
          ▼
  ┌──────────────────┐
  │  Terraform Core  │  差分計算・依存グラフ・state 管理
  └──────────────────┘
     │        │        │   プラグインとして呼び出す
     ▼        ▼        ▼
  [aws]   [github]  [cloudflare]   ← provider
     │        │        │
     ▼        ▼        ▼
  AWS API  GitHub API  Cloudflare API
```

### Terraform Core（CLI）

`terraform` コマンドそのものです。HCL を読み、現状との差分を計算し、どの順番で何をするかを決めます。

重要なのは、**Core 自身は AWS のことを何も知らない**という点です。S3 バケットの作り方も、EC2 の起動方法も知りません。

### provider

それを知っているのが **provider** です。「AWS の API をどう叩けばリソースを作れるか」を知っているプラグインで、Core とは別のバイナリとして配布されます。

第 2 章で「Terraform から見ればすべては API 呼び出し」と書きました。provider はまさにその API クライアントの塊です。だから **API さえあれば何でも管理対象にできます**。

- クラウド: AWS、Google Cloud、Azure
- SaaS: GitHub（リポジトリやチーム権限）、Datadog（監視設定）、Cloudflare（DNS）、PagerDuty
- その他: Kubernetes、ランダム文字列の生成、TLS 証明書の作成

「GitHub のリポジトリ設定を Terraform で管理する」というのは珍しい話ではありません。

### Registry

provider の配布場所が **Terraform Registry**（registry.terraform.io）です。npm レジストリに相当します。再利用可能な設定のまとまり（module、第 9 章）もここで公開されています。

`hashicorp/aws` のように `名前空間/名前` で識別され、HashiCorp 公式、パートナー製、コミュニティ製の区別が表示されます。

### npm との対比

| Terraform | Node.js の世界 |
| --- | --- |
| Terraform Core | Node.js ランタイム + ビルドツール |
| provider | npm パッケージ（ただし API クライアント専用） |
| Registry | npm レジストリ |

似ていますが、**provider はあなたのコードから import して呼ぶものではありません**。Core が裏で呼び出します。あなたが書くのは「何が欲しいか」だけです。

## 3.4 HCL と state

残りの 2 つの主役にも触れておきます。どちらも後で独立した章があるので、ここでは役割だけです。

### HCL — 書く側

HCL は JSON に近い構造を、人間が読み書きしやすくした**設定言語**です。変数や条件式、ループ相当の式はありますが、自由な関数定義やクラスはありません。

TS 使いからは「なぜ普通のプログラミング言語で書かせないのか」と思うかもしれません。これは意図的な制約です。**誰が書いても似た形になり、レビューで読みやすい**ことを優先しています。詳しくは第 5 章、他ツールとの比較は第 15 章で扱います。

### state — 覚えておく側

Terraform は、自分が作ったリソースを **state ファイル**に記録します。「コード上の `aws_s3_bucket.assets` は、AWS 上の `my-app-assets` というバケットのことだ」という対応表です。

React が前回のレンダー結果を覚えておいて差分を取るのと同じく、Terraform も**前回の結果を覚えているから差分が取れます**。

state は Terraform で最も重要で、最も事故が起きやすい部分です。第 8 章を丸ごと使って扱います。

## 3.5 基本のワークフロー

Terraform の作業は、ほぼ次のサイクルの繰り返しです。

```
 write ──▶ init ──▶ plan ──▶ apply
   ▲                  │
   └──── 直して再度 ◀─┘          （不要になったら destroy）
```

| ステップ | やること | Web 開発での感覚 |
| --- | --- | --- |
| write | `.tf` ファイルを書く | コードを書く |
| init | provider をダウンロードし準備する | `npm install` |
| plan | 現実との差分を計算して表示する | `git diff` / dry-run |
| apply | 差分を実際に適用する | デプロイ |
| destroy | 管理しているリソースをすべて消す | — |

`init` は最初の 1 回と、provider・module・state の保存先（backend、第 8 章）の設定を変えたときに実行します。日常的に回すのは **write → plan → apply** です。

各コマンドの具体的な使い方と出力の読み方は、次章で実際に S3 バケットを作りながら見ていきます。

## 3.6 plan が中心にある

Terraform の設計で最も特徴的なのは、**「適用する前に、何が起きるかを必ず見せる」**という点です。

`plan` を実行すると、Terraform は次の 3 つを突き合わせます。

```
  コード（あるべき姿）
          ＋
  state（前回の記録）    ──▶  差分 = 実行計画
          ＋
  現実（API で問い合わせた今の姿）
```

そして「1 つ作る、1 つ変更する、1 つ削除する」と、**実行される操作の一覧**を出します。

### なぜこれが重要なのか

インフラの変更は、アプリのデプロイよりも取り返しがつきにくいからです。

- データベースを消したら、中のデータは戻りません
- 本番のネットワーク設定を誤れば、全サービスが止まります
- ある設定値を変えただけで、**リソースが「削除して作り直し」になる**ことがあります（第 6 章）

シェルスクリプトでインフラを操作すると、実行してみるまで何が起きるかわかりません。Terraform は**実行前に影響範囲が文字で読める**。これが命令的なやり方に対する最大の利点です。

チーム開発では、この plan の結果を Pull Request に貼ってレビューし、マージしたら apply する、という運用が定番です（第 13 章）。**コードレビューの対象が「コード」だけでなく「起きること」にまで広がる**わけです。

### 代償: plan は完璧ではない

ただし、plan を過信してはいけません。

- plan は「provider が事前に予測できる範囲」の計画です。**API 側の制約違反などは apply して初めてエラーになる**ことがあります
- apply が途中で失敗すると、一部だけ作られた状態で止まります。データベースのトランザクションのような全体ロールバックはありません
- plan から apply までの間に誰かが別の変更をすれば、前提が崩れます

「plan で緑だったから安全」ではなく、**「plan で危険を見つけやすくなる」**と捉えてください。

## 3.7 得意なこと、苦手なこと

Terraform は万能ではありません。境界線を知っておくと、無理な使い方を避けられます。

### 得意なこと

- **クラウドリソースの作成・変更・削除**: VPC、データベース、ロードバランサ、IAM、DNS
- **サービスをまたいだ構成**: AWS のロードバランサの DNS 名を Cloudflare のレコードに登録する、といった連携
- **同じ構成の複製**: 開発環境と本番環境をほぼ同じ形で作る
- **変更の可視化と履歴**: Git に残り、plan で差分が見える

### 苦手なこと

**サーバの中身の設定**

EC2 のようなサーバを「作る」のは得意ですが、その中にパッケージを入れる、設定ファイルを置く、といった作業は守備範囲外です。これは Ansible などの**構成管理ツール**の領域です。

もっとも、最近はコンテナやサーバレスが主流で、「サーバの中に入って設定する」場面自体が減っています。

**アプリケーションのデプロイ**

新しいバージョンのコンテナイメージを本番に出す、といった作業は、Terraform でもできなくはありません。しかし実務では **CI/CD パイプラインや専用のデプロイツールに任せる**ことが多いです。

理由は頻度と性質の違いです。インフラの変更は週に数回、アプリのデプロイは日に何十回。後者を毎回 plan → レビュー → apply に通すと重すぎます。線引きの具体例は第 10 章で扱います。

**頻繁に変わるデータ**

ユーザごとに作られるリソースや、アプリが動的に作るものは管理対象に向きません。Terraform は「人がコードで決めるもの」を扱う道具です。

---

## まとめ

- Terraform は「あるべき姿」を HCL で宣言し、**現実との差分を埋める**ツール
- 2023 年に BSL へライセンス変更され、フォークとして **OpenTofu** が生まれた。2025 年に IBM が HashiCorp を買収した
- **Core は差分計算、provider は API 操作**を担う。API があれば AWS 以外も管理できる
- provider や module は **Registry** から取得する。npm レジストリに近い
- **state** は「コードと現実の対応表」。差分計算の要
- 基本は **write → init → plan → apply**。中心にあるのは「適用前に影響を見せる」plan
- サーバ内部の設定やアプリのデプロイは、**他のツールに任せる**ほうがうまくいく

次章では、実際に Terraform をインストールし、S3 バケットを 1 つ作って消すまでを通して体験します。
